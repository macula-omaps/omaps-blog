2027 年企业 IT 部门的方向：上下文厚度与研发范围重构

2026-11-13
AI 原生研发
共 4217 字 · 阅读约 9 分钟
0 次浏览

这是年度规划稿：明年做什么、为什么是这几件、做到什么程度算完成。文中不带具体项目和客户信息，方法谁都能用。

先给结论

2027 年的重点不是换更好的模型。模型谁都能买，一年一年看下去，在选模型这件事上多花心思，回报越来越低。真正拉开差距的是两件事，外加一条不能破的底线：

方向要做到什么怎么算完成
上下文厚度AI 越用越懂业务，组织记忆能攒下来、随时调问「这个项目现在什么情况」，不用再翻记录、开会问人
研发范围重构研发的活从写代码扩到流程自动化、对话式服务研发接的需求不再只有系统工单
底线Agent 直连系统后，防护从界面挪到服务端五类绕过逐项有闸，接系统和设闸同步完成

目标底下才是措施。想让 AI 懂你的业务，就得把数据、规则、干活留下的痕迹，喂到它够得着的地方。这件事主要靠接系统，另外还有三条路：给老系统反向提取规则基线、把工作产物回流入库、需求收集用结构化表格。其中接系统的工程量最大，而且接了系统 Agent 就直连了数据，安全闸必须跟着走，所以那条底线不是可选项。至于研发范围重构，决定的是这些活由谁干、怎么干。

一、为什么上下文厚度是主线

先说一个当标尺用的公式：

组织竞争力 = 人才密度 × AI 杠杆 × 上下文厚度 ÷ 组织摩擦

四个变量里，上下文厚度是唯一花钱买不来的，只能一年一年攒。注意别把它理解成把文件都塞给 AI——没有版本、没人负责、不知道可不可信的资料，塞得越多模型错得越自信。有用的上下文就四类：

类型装什么缺了会怎样
可信材料原件、卷宗、客户档案、业务系统里的真实数据AI 拿二手转述当依据
有效规则业务口径、期限规则、规范、禁止项每次输出都得人工重讲一遍规则
可复用方法提示词、Skill、方法论、作业流程好做法留在个人手里，人走了方法也走
持续反馈专业核验、局部修正、版本更新、复盘错误被反复复制，没人纠正

组织用 AI 的水平可以分层：L1 超级个体（个人）、L2 超级团队（部门流程重构）、L3 超级记忆（全公司上下文）、L4 超级大脑（决策层汇总）。多数组织的现状是 L1 跑得挺快，L3 完全空白——问个项目情况，还是靠人翻记录、靠开会同步。

2027 年的钱和人应该压在 L3。想跳过 L3 直接做 L4，做出来一定是假的：底下没有完整的上下文，给决策层的汇总只能靠猜。

而这四类东西的来源，几乎全在系统里。业务数据在业务系统里；规则散落在工单、制度文件和老师傅的脑子里；反馈在审批和复盘的流程里。所以做厚上下文的措施有四条，明年全都要动：

  1. 接系统——主措施，工程量最大，下一节单独说；
  2. 给存量系统反向提取基线——把散落在老系统里的规则沉淀下来，见第三节；
  3. 产物链回流——每次干活的产物自动归档，变成下一个人的输入，也在第三节；
  4. 结构化需求收集——需求本身就是上下文的入口，见第六节。

接系统之所以值得单独一节，一是它工程量最大，二是它同时把安全面打开了——第四节整节讲的就是这件事的另一面。

二、接系统：做厚上下文的主措施

先说一个常见的错：把接入当成「给 AI 配工具」。配工具的思路是调通就算完；我们说的接入是给上下文修管道。每接一个系统，五个问题得先答上来：

问题回答什么答不上来会怎样
哪些数据可信到能直接当依据可信材料的边界AI 拿脏数据当事实往外说
写操作由谁拦服务端闸装在哪Agent 替用户摸出不该走的路
身份怎么透传调用者身份 on-behalf-of审计对不上号，权限还被放大
操作在哪留痕审计记在哪出了事说不清谁干的
出口怎么脱敏敏感字段统一打码数据从 AI 通道漏出去

分级接，默认只读起步

不是所有系统都要一步到位。分三级，一级一级解锁：

级别干什么前提
只读查询、检索、汇总、报告数据域闸 + 脱敏出口
受控写走系统里已有的业务方法（带状态闸、字段白名单）服务端闸全绿 + 高危动作人点头
自主写Agent 自己发起变更暂不开放；要开，先过威胁建模

从只读开始。只读阶段就把身份透传和审计做对，以后升受控写，只需要补闸，不用推倒重来。

每个系统登记七项

接没接，不能靠口头说。每个系统落一份登记，七项缺一不可：系统名称、接入范围（开哪些端点和工具）、身份方案（透传调用者，不开共享账号）、数据域闸装在哪、审计记在哪、脱敏出口在哪、负责人和生效日期。这份登记本身也是上下文——「我们哪些系统对 AI 开着、开到什么程度」，从此是一个能直接回答的问题。

排顺序看场景，不看系统大小

先接哪个系统，不按系统的重要程度排，按场景的成熟度排。三道闸门，缺一道就不开工：

  1. 输入拿得到——材料、数据、样例在授权范围内能拿到；
  2. 规则说得清——口径、期限、规范、禁止项能讲明白；
  3. 结果核得了——专业的人拿着原始材料能判断对错。

一般高频、耗时、重复、边界清楚、容易验收的场景先上。反过来有几件事要明确划在红线外：对外定稿、专业结论、付款审批、对客承诺、质量放行——AI 负责准备材料、组织证据，签字的还是人。

接完的标准

一个系统接完了，标准不是「调通了」，是这四项全到位：闸在服务端、身份在认证态、操作有留痕、出口有脱敏。少一项都别上线——那不是接了个能力进来，是留了个事故入口。

三、把研发流程固化下来

工具进团队是第一年的事。第二年要做的是把 AI 从「个人加速器」变成默认的研发流程。上面说的产物回流、基线提取，载体都在这套流程里。抓手是验证过的三件套：

  1. 产物链：intent → spec → plan → diff+tests → PR → incident 回流。下一个环节读的是上一个环节留下的文件，不是「上次咱们聊的」。
  2. 三值门禁：PASS / BLOCKED / UNKNOWN，UNKNOWN 一律不放行；干活的和检查的分开；每个门禁上线前双向验证，该拦的拦得住，该放的放得过。
  3. 三层度量：AI 效能、工程质量、价值交付，配上 Session → Commit → Change → Workitem 这条对账链——链断了，「提速到底是不是 AI 带来的」就永远说不清。

还有两件基础活，2027 年接着做：

  • 给存量系统反向提取基线。老系统没有不变量文档，AI 直接进去只会把混乱加速放大。提取的时候注意，低置信度的「历史妥协」不要固化成规则，单独记到风险项里，否则等于把 Bug 合法化了。
  • 试点期先当众认账：允许慢 20%。等进度落后了再说这话，没人信，流程当天就散。

四、底线：Agent 直连系统后的权限闸

这是接系统的另一面，也是 2027 年架构改造清单的来源。核心问题一句话：AI 把企业系统的用法从「人点界面」变成了「agent 直接调 API」，过去默认由界面承担的防护，一下子全没了。

具体塌在哪三个地方：

  1. 裁剪没了。Agent 眼里没有「你的界面」，只有全部 API。界面上没有入口，不等于系统里没有入口。
  2. 「该不该」没人答了。用户跟 Agent 说「把这个号从 A 改成 B」，Agent 会去找怎么改，不会去想该不该改。它忠实、高效、不质疑。
  3. 合法身份加忠实执行，最危险。不用外面来攻击者：自己人一句含糊的指令，就够 Agent 替他把所有隐性约束都绕过去；事后查日志，看到的还是合法用户、合法凭证、合法接口。

落到工程上，就是五类绕过。每接一个系统，这五条就是五条验收项：

#绕过类型判断标准
1垂直越权有没有资格调这个接口
2水平越权（IDOR）有没有资格动这条数据
3状态前置绕过单据现在这个状态，允不允许做这个动作
4命令通道越权命令链路上每一道闸都在吗
5业务组合约束绕过改完之后字段组合还合法吗

三条原则，2027 年不讨论、不例外：

  • 闸全部装在服务端。能写成脚本的规则，就不要写成提示词。提示词只是提高遵守的概率，服务端闸才是保证。
  • 身份永远不从提示词和参数里来。调用者身份从认证态一路透传；谁提「给通道配个共享账号」，一律否掉。
  • Agent 算一个正经身份。有自己的凭证、自己的审计记录、自己的行为基线，管它的强度和管人的账号一样。

防的形态没变，验收标准变了：闸不光要挡得住外面的攻击，还要挡得住自己人的 Agent 替他摸出来的所有路径。评审的时候，凡是「界面上没入口所以没事」这种回答，一律不算数。

五、研发范围重构：从写代码到管流程

前面说的是 AI 怎么用，这一节说研发的人干什么。

传统研发的需求来源是系统工单：业务提需求，研发排期做。2027 年需求来源要多出两类：

  • 流程自动化：跨系统的业务流程交给 Agent 编排。研发的活从「实现功能」变成「把流程画清楚（谁触发、读什么、判断什么、写什么、出了错谁兜底），然后决定哪一段交给 Agent」。
  • 对话式服务（数字人）：以对话形态直接对外的 AI 员工，背后接的就是第二节的系统通道。对话入口说到底是个新界面，而这个界面没有裁剪能力——它能调的每个能力，都得靠第四节的闸看着。

对工期的理解要更新

AI 把编码接走之后，工期结构变了，排法也得跟着变：

阶段过去2027 年
需求澄清很短，口头加工单变重——intent/spec 成了正式环节
编码实现占大头，按人天排大幅压缩，按会话并行排
评审验收常常被压缩变重——大 diff 成了常态，评审是新瓶颈
流程定义不算研发的活新增——流程自动化项目的主要工作量

总工期会缩短，但不是均匀缩的：头尾（澄清、验收）变重，中间（编码）变轻。排期要是还按「编码人天」估，恰恰把最需要花力气的两头估没了。

六、组织机制：让协作本身留下上下文

机制不是虚的，它决定前面这些活谁推、推多快。

三句话汇报。问题上报固定三句：

  1. 问题是什么；
  2. 我的方案是什么；
  3. 下一步打算干什么，需要哪些授权和资源。

问题要及时报。报得晚，能选的路就少，这是要授权、要资源的唯一窗口。这个格式还有个好处：三句话写下来就能归档、能检索，下一个遇到同样问题的人直接拿去用。

双向培训。研发给业务讲 AI 能干什么、边界在哪、哪些场景接得了；业务给研发讲业务口径、期限规则、异常怎么处理。能力要留在业务侧：业务骨干自己动手搭场景，研发做支持、陪着跑，别代劳——代劳一次，这个能力就永远长在研发手里了。

需求收集用结构化表格。年度需求收集用在线表格收，不收大段自由文本。背景、目标、验收标准、涉及系统、期望时间，一个字段一个字段填。填出来的东西既是排期依据，也是 intent.md 的原料——收集需求这个动作本身，就在给上下文做增量。

最后

2027 年年底盘点，就看三条：

  1. 上下文有没有变厚——接了几个系统、多少规则进了基线、多少产物回流成了能复用的方法；
  2. 闸有没有跟上——每个接入系统的五类绕过验收项是不是全绿，有没有「先接着、闸后补」的欠账；
  3. 工期预期有没有更新——排期口径是不是已经从编码人天换成了澄清加验收。

模型每年都在变强，但这三条不会因为模型变强就自动完成。装上工具是第一天的事，把目标、措施和底线落成清单、闸和度量，才是 2027。
